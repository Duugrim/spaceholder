# Утилита баланса (`tools/balance`)

Локальная веб-утилита для переработки баланса урон ↔ броня ↔ HP. Нужна, чтобы **сначала договориться о логике** («пистолет в голову без брони — смерть, но не всегда»), а потом уже подбирать числа и формулы под эти случаи. Три раздела: **Случаи**, **База**, **Калькулятор**.

Запуск: `tools/balance/Start Balance Tool.bat` или `npm run balance` → <http://127.0.0.1:8766>. Закрытие окна останавливает сервер. Зависимостей нет (Node 20+, модуль `http`).

## Случаи

Дерево: **тип оружия** → **случай** (оружие + патрон против части тела) → **варианты**. Свёртываются на каждом уровне; состояние запоминается в браузере.

Вариант — это строка: броня · сторона (спереди / сбоку / сзади) · дистанция в метрах (по умолчанию 0, в упор) · условие (текст) · исход для цели · примечание («почему так»).

- **Исход** — то, что происходит **с целью**; выбирается из выпадающего списка (шкала в «Справочниках»: смерть → часть тела уничтожена → смертельная травма → тяжёлая → лёгкая → задел → остановлена). Кнопка «+» рядом даёт **второй исход**: первый становится ☠ красным черепом (худший исход для цели), второй — ♥ зелёным сердцем (лучший исход для цели). Если «лучший» тяжелее «худшего», появляется «⇅» поменять местами.
- **Сторона «сбоку»** в текущей механике считается как «спереди»: у пресетов анатомии только грани `front` и `back`, а резолвер для неизвестного направления берёт первую грань (в игре боковых попаданий тоже нет — `clockToHitFace` отдаёт только front/back). Когда понадобятся настоящие боковые удары, нужны боковые грани у частей и броня на них.
- **Броня** — «Без брони», набор слоёв (пресет), предмет из игры или «Свои слои…» (материал + толщина в мм, с подписью). Набор — не предмет Foundry, а заготовка из слоёв; создаётся на вкладке «База» → «Наборы слоёв».
- «+ По броне и дистанциям…» создаёт варианты сразу для нескольких броней и дистанций (дубликаты пропускаются).
- **Что стреляет.** В шапке случая — патрон из базы и (необязательно) оружие из базы. С патроном и оружием считается только это оружие; с одним патроном — **семейство** (галочка «семейство», по умолчанию включена): все оружия базы с той же группой, что тип оружия случая (Пистолеты, ПП…), под калибр этой группы патронов, и все патроны группы. Так «пистолет не всегда пробивает каску» считается как разброс по разным пистолетам и патронам, а не бросок. Оружие ближнего боя без патрона: в варианте выбирается удар (линия; «любой удар» — все линии оружия, худший и лучший по ним) и сила атакующего (СИЛ, 100 — средний человек).
- **Цель варианта.** «одна цель» или «вторая за первой»: пуля сначала проходит первую цель (без брони, та же часть), остаток идёт во вторую — броня варианта на ней.
- «Сверка с механикой» добавляет колонку **«Сейчас»**: значок сверки (✓ совпадает, ≈ в пределах договорённого, ✗ расходится), урон в часть и долю её HP, и ☠/♥ — **худший и лучший исход механики** по той же шкале. Подсказка у ячейки: вероятность, оружие, куда попало (щель брони, задетые органы), причины (доля HP, органы, кровотечение) и распределение исходов по каждому оружию. Сегмент «✗» оставляет расходящиеся варианты, счётчик «✓ · ≈ · ✗» — в панели. Как считается — «Сверка» ниже.
- **Предложено ИИ.** Вариант с `proposed: true` (у случая — тоже `proposed: true`) добавил ИИ: исход и примечание — его догадка. Такие варианты отмечены синей полосой и значком «ИИ», сегмент «ИИ» в панели оставляет только их, счётчик «предложено ИИ: N». «✓» у варианта принимает его (флаг снимается), «Принять всё» — все варианты случая; у случая без непринятых вариантов значок пропадает. В экспорте такие строки помечены «[ИИ]».
- «▶» в строке открывает вариант в калькуляторе.
- Удаление не спрашивает подтверждения: внизу появляется «Отменить».

База случаев стартует почти пустой: один пример из диктовки — «Пистолет (9×19) → Голова» (без брони, метр стали, 100 м) без исходов. Типы оружия, случаи и варианты добавляются в интерфейсе («+ Тип оружия», «+ Случай», «+ Вариант»); пустые типы показываются одним заголовком. Старая таблица случаев осталась в карточке `docs/Kanban/S-XL Баланс HP частей анатомии.md`, раздел 7.

**Цвета.** Материалы окрашены везде, где встречаются (теги слоёв брони, список материалов, редактор слоёв, таблица слоёв в калькуляторе); типы урона, части тела и типы оружия получают свой акцент. Цвета заданы в `web/js/icons.js` (`materialColor` по слагу материала с запасным цветом по категории).

## Сверка (`lib/outcome.mjs`)

Исход механики считается тем же кодом, что и состояние тела в игре: раны → `applyBodyState` → `classifyOutcome` (`module/helpers/body-state.mjs`: часть потеряна — «Часть тела уничтожена», с пометкой «смерть», если это убило; мёртв — «Смерть»; при смерти — «Смертельная травма»; худшая рана ≥ 30% HP части или задет не жизненно важный орган — «Тяжёлая»; ≥ 5% — «Лёгкая»; хоть 1 HP — «Задел»; иначе «Остановлена»).

- **Место попадания** — единственная случайность. Резолвер спрашивает про каждый бросок (щель в броне, каждый орган) через `decide`; сверка проходит **все ветки** с их вероятностями (`enumerateBranches`). Исходы одного оружия складываются; худший и лучший берутся среди исходов не реже 2% (`MIN_OUTCOME_P`). Случаи описывают **точное** попадание, поэтому выстрел (патрон) в сверке всегда приходит в пластину — щели брони разыгрывает только ближний бой (клинок ищет щель); в живой игре щель выпадает у всех.
- **Дробь**: если веер у цели не шире 0,5 м (`VOLLEY_SHARED_SPREAD`, как в игре) — все дробины одной раной; шире — в часть попадает доля дробин (часть ~0,35 м), каждая отдельной раной.
- **Взрыв** (`onHitSplash` у патрона): кроме попадания — взрыв по части и её соседям (`adjacent`), до 3 частей, энергия делится.
- **Сверка** (`verdict`): ✓ — оба края совпали; ≈ — исход механики внутри договорённого диапазона и один край совпал; ✗ — иначе. «Часть уничтожена (смерть)» совпадает и со «Смертью», и с «Частью уничтожена».
- Не считается («—»): у случая нет ни патрона, ни оружия из базы, или часть тела без слота.

## База

Материалы, боеприпасы, оружие, броня и наборы слоёв. Записи из компендиума хранят два набора значений:

| Поле | Смысл |
|---|---|
| `base` | что сейчас в игре (снимок при импорте) |
| `values` | рабочая копия, её правит баланс; калькулятор по умолчанию считает по ней |

Изменённое поле подсвечивается и показывает «в игре: …»; «Сбросить к игровым» возвращает `values = base`. Статус записи: **черновик** (значения взяты из игры как есть, целью баланса не считаются) → **в работе** → **утверждено**. Свои записи (`source.type: custom`) можно создавать и дублировать.

- «Обновить из компендиума» — подтянуть предметы из `pack-src/sh-test-items`. Новые приходят черновиками; у существующих `base` обновляется, а `values` следует за ним, только если вы их не правили (иначе запись помечается «игровые значения изменились»).
- «В компендиум…» — **опционально**: записать изменённые `values` обратно в JSON `pack-src/sh-test-items` и (отдельной кнопкой) выполнить `npm run pack:sh-test-items`. Магазины и ячейки («Магазин 9×19-S») несут свою копию патрона — из неё и стреляет оружие, поэтому при записи патрона его магазины (тот же калибр и те же значения, что были у патрона) получают те же урон, спад, залп и взрыв; в плане они видны отдельными строками. Записи читаются в порядке компендиума (`sort`): из двух патронов одного калибра простой id (`ammo.9mm`) у первого в папке, второй получает id с именем (`ammo.9mm-патрон-9x19-бронебойный`). Сборка в LevelDB требует закрытого Foundry. Два файла (`SH_Material_concrete`, `SH_Material_rock`) форматированы не так, как `JSON.stringify`, — при записи в них в git появятся лишние строки diff.

## Калькулятор

Выстрел по линии: **патрон** (можно «из оружия» — множитель энергии линии) или **собственный урон оружия** (ближний бой, лучевое; усилие = СИЛ) → **стены** (набор слоёв или свои слои, дистанция) → **цель** (часть тела, сторона, броня, энергия попадания, число попаданий подряд, своё HP).

Порядок расчёта повторяет боевой:
1. записи урона патрона (+ `energyMult` оружия) → применения с готовой энергией `урон × (пробитие/100)² × твёрдость`;
2. до каждого элемента — **спад по дистанции**: энергия × `0,5^(d/полураспад)`, урон следует за энергией, пробитие не меняется (как в живой атаке). Спад считается от дула и применяется постепенно, так что остаток после стены продолжает падать;
3. стена: `passSpan` (по слою на каждый слой набора); не пробита — выстрел кончается;
4. цель: энергия попадания (`applyEnergyScaleToApplications`), затем `resolveBodyTraversal` по анатомии `humanoid`: броня, ткань части (часть получает поглощённое), органы, что вышло из тела. У каждого попадания серии — рана (`wound`: урон снаряда, удар, энергия полости, дошёл ли до органов, вышел ли), задетые органы (`organs`) и остаток снаряда (`exit`).

Результат: по шагам — что было у снаряда до и после (урон, энергия), итог по части тела (урон, доля HP, по типам, части за ней), **исход** по шкале случаев (при бросках органов — один вариант места попадания; все варианты считает сверка), удар, задетые органы, что вышло из тела, кровотечение, износ слоёв брони, серия попаданий с **HP части** (насыщение, «не работает» ниже 0, «уничтожена» ниже −запаса) и **состоянием цели после каждого** (раны копятся), таблица слоёв (пробит/держит). «Занести в случаи» добавляет сценарий вариантом в базу случаев.

Не считается (долгосрочно): несколько целей на линии (остаток после выхода из тела не возвращается резолвером), взрыв при попадании и АоЕ, несколько лучей дроби (считается один луч).

> **Спад в живой атаке.** Спад применяет `ShotManager.applyImpactsToActors`; `AimingManager._resolveHitImpacts` (путь реальной атаки) его не вызывает, а `_applyResolvedProjectileDamage`, который вызывает `applyImpactsToActors`, нигде не используется. Похоже, в игре спад по дистанции сейчас не действует — калькулятор считает его так, как задумано (галочка «Спад по дистанции»). Проверить в Foundry.

## Экспорт для ИИ

Кнопка «Экспорт для ИИ» собирает `tools/balance/exports/balance-cases.md`: все случаи с выбранными исходами, колонками «Механика» (худший / лучший исход механики, урон и доля HP) и «Сверка», итогом сверки вверху и справочником патронов, наборов и материалов, на которые они ссылаются. В «Условии» видно, что механика берёт из варианта: вторую цель, удар и силу. Это то, что отдаётся агенту, чтобы подобрать числа и механику под договорённые исходы.

## Данные и сервер

| Что | Где |
|---|---|
| Данные | `tools/balance/data/{cases,items,dictionaries}.json` — в git |
| Резервные копии | `tools/balance/data/.backups/` — при каждом запуске, последние 15 каждого файла (не в git) |
| Экспорт | `tools/balance/exports/` (не в git) |
| Веб | `tools/balance/web/` — ES-модули без сборки |
| Сервер | `tools/balance/server.mjs` + `lib/` (`store`, `compendium`, `engine`, `export-md`, `seed`) |

Правки сохраняются сами через 0,5 с. Каждый документ несёт `revision`; запись с устаревшей ревизией отклоняется (HTTP 409), страница предлагает перезагрузиться, чужие правки молча не затираются. Сервер слушает только `127.0.0.1` и отвергает чужие `Host`/`Origin`.

Первый запуск создаёт файлы данных: справочники, предметы (импорт из `pack-src` + наборы слоёв, скопированные из игровой брони и стен) и пример случая. Чтобы начать с нуля — удалить `tools/balance/data/*.json`.

## Тесты

```bash
node tools/balance/test/engine.test.mjs      # симулятор: согласие с резолвером, спад, стены, серия
node tools/balance/test/outcome.test.mjs     # сверка: ветки места попадания, семейство, вердикт, дробь, взрыв, вторая цель
node tools/balance/test/store-api.test.mjs   # хранилище, импорт/запись в pack-src (во временной папке), HTTP API
```

Тесты не читают компендиум ради чисел (материалы — из `__fixtures__/test-materials.mjs`), а импорт и запись проверяют на копии нескольких файлов во временной папке.
