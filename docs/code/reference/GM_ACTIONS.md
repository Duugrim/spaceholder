# Менеджер действий ГМа (`gm-actions`)

Единый путь для всего, что клиент игрока должен сделать **с правами ГМа** (первый потребитель — урон по токену, которым игрок не владеет). Не связан с одобрением ГМом-человеком (журналы, глобальная карта): тут ГМ ничего не решает, пока не появится очередь «в отсутствие».

Код: `module/helpers/gm-actions/`. Вход — `installGmActions()` на `ready` (`spaceholder.mjs`), API — `game.spaceholder.gmActions`.

## Как это работает

```
игрок: request(type, payload, { label, chatMessageId })
 ├─ ГМ-клиент сам → выполняется сразу
 ├─ есть активный ГМ → сокет → ГМ подтверждает (ack ≤ 3 с) → выполняет → ответ игроку
 └─ ГМ нет / не подтвердил → очередь в флагах СОБСТВЕННОГО User игрока + пометка в чате
```

- **Один исполнитель.** Живой запрос обрабатывает только назначенный ГМ (`game.users.activeGM`); второй ГМ молчит.
- **ack — не одобрение.** Это автоматическая квитанция «клиент ГМа получил запрос», её шлёт код, а не человек. Пока ГМ в сети, он ничего не решает и ничего не видит: действие просто выполняется. Единственное место, где ГМ-человек что-то решает, — окно очереди (ниже), и только для действий, оставленных, когда ГМа не было.
- **Нет ack за 3 с → очередь, есть ack → ждём результат** (до 30 с), в очередь *не* кладём (мог уже выполниться). Ошибка handler'а или отказ `validate` приходят игроку как ошибка.
- **Занятый ГМ ответил поздно.** Если запрос дошёл до ГМа уже после того, как игрок положил копию в очередь, ГМ-клиент помнит id выполненного (`_handled`: `running` / `done` / `failed`): копия **не выполняется второй раз**, а только вычищается, заметка в чате ставится по факту (снята или «не удалось»). Это же работает, если ГМ нажмёт «Применить» на такой записи в окне; «отмена» уже выполненного действия невозможна — запись просто убирается.
- **At-most-once.** Запись удаляется из очереди *до* запуска handler'а; повторный запрос с тем же id игнорируется.
- **Очередь.** `flags.spaceholder.gmQueue.<id>` на User игрока (игрок может писать только в свой User; хранится между сессиями, ГМ читает чужие). Запись: `{ id, type, category, label, payload, requesterId, requesterName, chatMessageId, createdAt }`.
- **Вход ГМа.** На `ready` назначенный ГМ видит окно **«Действия игроков в ваше отсутствие»**: записи по категориям (урон, глобальная карта, прочее), у каждой группы и записи — галочка. «Применить выбранное» — отмеченные применяются по порядку создания, **неотмеченные отменяются**; «Позже» — очередь остаётся (`game.spaceholder.gmActions.openQueue()` откроет снова).
- **Пока ГМ в сети**, записи, появившиеся уже после входа (клиент на миг потерял ГМа), применяются сами (`updateUser` → `processLive`); бэклог входа в них не попадает.

## Заметка в чате

`flags.spaceholder.gmActions` на сообщении — карта `{ [entryId]: 'pending' | 'cancelled' | 'failed' }`; хук `renderChatMessageHTML` дописывает строку:

| Состояние | Строка |
|-----------|--------|
| ждёт | «Действие ожидает ГМа» (при нескольких — «Действия ожидают ГМа (N)») |
| успешно применено | строка исчезает (ГМ снимает флаг) |
| отменено ГМом | «Отменено ГМом» |
| не удалось / отказ `validate` | «Действие не удалось» |

Заметка вешается на `chatMessageId`, который передал вызывающий. Если сообщение нельзя изменить (нет прав) или id не передан, создаётся отдельное маленькое сообщение с `label`. Выстрел id не передаёт (сообщения выстрела больше нет — запись об атаке пишется только при выходе из прицеливания), поэтому каждое отложенное попадание — своя заметка «кто → кого (часть)». Живые запросы (ГМ в сети) заметок не создают.

## API

```js
// выполнить с правами ГМа (на любом клиенте)
const r = await game.spaceholder.gmActions.request('damage.apply', payload, { label, chatMessageId });
// r = { status: 'done', id, result }  |  { status: 'queued', id }

// зарегистрировать тип (на КАЖДОМ клиенте: игроку нужна категория, ГМу — handler)
game.spaceholder.gmActions.register('my.action', {
  category: 'misc',                 // группа в окне очереди; метка: SPACEHOLDER.GmActions.Category.<id>
  validate: async ({ entry, payload, requester }) => true,   // true или строка-причина отказа
  handler: async (payload, { entry, requesterId, requester }) => result,   // малый JSON-результат
});

game.spaceholder.gmActions.listQueue();   // записи очереди (ГМ)
game.spaceholder.gmActions.openQueue();   // окно очереди (ГМ)
```

Требования: `payload` и результат — чистый JSON (идут через сокет и лежат во флаге); `label` — человекочитаемое описание уже локализованной строкой; тип регистрируется до первого запроса. Системные типы — `gm-action-handlers.mjs` (`GM_ACTION_TYPES`, `GM_ACTION_CATEGORIES`).

## Типы действий

| Тип | Категория | Что делает | Проверка |
|-----|-----------|------------|----------|
| `damage.apply` | `damage` | `Actor#applyDamagePackage` на цели (мир-актёр или токен-актёр по uuid) | запросивший владеет атакующим из `source.attackerUuid` (ГМ — всегда) |
| `journal.appendLine` | `misc` | Дописать строку в журнал раунда ходящего персонажа (`action-chat-journal.mjs`, `applyJournalAppendLineAsGm`) — реакция игрока не в его ход | запросивший владеет действующим персонажем `actorUuid` |
| `journal.replaceMessage` | `misc` | Перевыложить сообщение журнала с новыми строками (отмена действия, сводка раунда): ГМ сам строит HTML из `journalFlags` | запросивший владеет персонажем, на которого ссылаются строки журнала |

Урон: `AimingManager._applyDamage` — владельцы цели (в т.ч. ГМ) применяют напрямую, остальные идут через менеджер.

Журнал раунда: сообщение принадлежит тому, кто его выложил (создать с чужим `author` и удалить чужое нельзя), а указатель «сообщение этого раунда» — флаг на анкерном актёре. Поэтому игрок, который не автор и не владелец анкера (реакция в чужой ход, отмена в сообщении, выложенном ГМом), не пишет сам: `appendCombatActionJournalLine` / `_replaceJournalMessage` отдают запись ГМу. Без ГМа запись встаёт в очередь с заметкой в чате «Журнал действий: …». Развёрнутость группы движений у неавтора меняется только в его окне чата.

## Безопасность

Сообщения сокета Foundry **не аутентифицируются** (заявленный `userId` можно подделать), поэтому `validate` защищает от ошибок и случайных чужих действий, а не от враждебного клиента. Записи очереди надёжнее: они лежат в User самого запросившего, а писать туда может только он (и ГМ).

## Устройство и тесты

| Файл | Роль |
|------|------|
| `gm-actions-core.mjs` | чистая логика: запись очереди, порядок, группировка, решение «применить / отменить» |

Журнал: `node module/helpers/actions/action-chat-journal.test.mjs` — кто пишет журнал сам, а кто через ГМа.

## Что не переведено

В системе остались отдельные копии «запрос ГМу по сокету» (каждая ждёт 8 с и падает, очереди нет): `item-piles-sh/socket-adapter.mjs`, `timeline-v2.mjs`, `minigames/lockpick/lockpick-chat.mjs`, `combat/combat-session-manager.mjs`. Их можно перевести на `register` + `request`, получив очередь и заметки в чате; пока работают как раньше.
